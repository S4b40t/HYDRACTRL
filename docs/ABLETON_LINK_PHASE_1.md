# Ableton Link feasibility · Phase 1

Use a separate native helper, supervised by Electron main. The prototype exercises the official SDK and the main-process boundary using private stdin/stdout pipes. A development launch opts in by setting `HYDRACTRL_LINK_PROBE` to the absolute path of a locally built helper. The probe writes diagnostics to the desktop log. It has no settings, sketch API, renderer integration, or installer step.

The base is `dxviie/HYDRACTRL:main` at `e494cfbb246c53ebe4f05f4527f2e4498e117fca`, which matched the fork's `main`. At inspection, the fork had unmerged MIDI, Signature Assist, and portable integration branches. Upstream had one open PR, the fork's Signature Assist work. The prototype branch does not incorporate those changes. [Upstream base](https://github.com/dxviie/HYDRACTRL/commit/e494cfbb246c53ebe4f05f4527f2e4498e117fca) · [Upstream PR #28](https://github.com/dxviie/HYDRACTRL/pull/28)

## Architecture and delivery choice

- The editor registers built-in plugins through `PluginHost` in `src/client/index.js`. `DesktopMirrorPlugin` routes sketch runs to the primary output while mirror frames are available, stops the editor's local render loop, and restores local rendering when the mirror drops. The Electron main process creates the texture-bridge window at `/output?primary` with background throttling disabled. `src/client/output.js` initializes its own Hydra and executes sketches through `createPrimaryRunner`. The Bun `outputHub` routes `run` and `result` messages and replays sketch, XY, audio input, and overlay state. The editor's preload exposes desktop controls and mirroring. The offscreen bridge is created without that preload. [Plugin system](PLUGINS.md) · [Desktop mirror](../src/client/plugins/DesktopMirrorPlugin.js) · [Spout window](../desktop/src/main/output.js) · [Output page](../src/client/output.js) · [Hub](../src/server/outputHub.ts) · [Preload](../desktop/src/preload/desktop.cjs)
- In Phase 2, Electron main should own one helper and cache its latest timestamped state. Give the editor and the bridge's primary window a narrow read-only Electron IPC endpoint through their sandboxed preloads. The installed texture-bridge 0.15.0 passes supplied `webPreferences` to the offscreen window and exposes `renderWindow.webContents`. Use those hooks to attach a preload and validate the exact window and origin in main. Let each renderer calibrate its clock and request the latest state when it is created or reloaded, so Spout restart and editor fallback use the same session. Keep timing independent of sketch traffic and the LAN-accessible output hub. Test the offscreen preload and sender identity on Windows before adding the optional plugin. [Desktop IPC](../desktop/src/main/ipc.js) · [Desktop lifecycle](../desktop/src/main/index.js) · [Current sender validation](../desktop/src/main/windows.js)

| Consideration | Helper executable | Native Electron module |
| --- | --- | --- |
| Complexity | C++17 and a versioned pipe protocol. Main supervises one child. | Node-API bindings, cross-thread handoff from Link's callbacks, and teardown of native state inside Electron. |
| Compatibility | One executable per OS and architecture, independent of Electron's ABI. | Node-API can reduce ABI churn. Builds still need target-specific binaries, Electron load tests and Windows linking verification. |
| Crash isolation | A native failure ends the helper. Main and rendering keep running. | A native fault in main can terminate the desktop session. |
| Latency | A pipe round trip calibrates the clock. Each render head can evaluate the timeline locally. Linux measurements below. | Direct native calls remove the pipe hop in main. The sandboxed render heads still need a clock mapping and IPC. |
| Windows packaging | Ship a versioned x64 `.exe` under `resources`, outside the ASAR. | Ship an unpacked x64 `.node` and associated dependencies. Current electron-builder rebuilds are disabled. |
| License and maintenance | Easier to identify the SDK-bearing component and its source obligations. IPC alone does not settle the license analysis. | In-process linking makes the SDK combination explicit and ties native release testing more closely to Electron. |

The helper has the lower integration cost for periodic snapshots. Linux pipe measurements support that choice. Windows measurements during the actual show workload remain open. [Electron native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules) · [Packaging configuration](../desktop/electron-builder.yml)

## Timing contract

The helper enables ordinary Link discovery, leaves start/stop sync disabled, and reads `captureAppSessionState()` without committing state. The SDK needs a seed tempo of 120 BPM for its standalone timeline. Joining and settling use the SDK's peer-to-peer negotiation. Live supplies the operational tempo when it follows the party input. Link gives no peer master status. `enabled: true, peers: 0` means no other session peer has been discovered. A process exit, invalid response, or timeout is a separate failure. A zero count alone cannot diagnose Windows firewall or interface restrictions. [SDK API](https://github.com/Ableton/link/blob/Link-4.1.1/include/ableton/Link.hpp) · [Live synchronization manual](https://www.ableton.com/en/manual/synchronizing-with-link-tempo-follower-and-midi/)

Each `sample` line requests one JSON line. Use one outstanding request per child. `quit` or stdin EOF disables Link and closes the helper. The app waits for exit during shutdown and terminates an unresponsive child after one second. It stops the probe on a missing reply or invalid response. The prototype leaves helper restarts to the next app launch. The running SDK rediscovers peers on its own.

```json
{"version":1,"hostUs":7500000,"bpm":120,"beat":11.75,"phase":3.75,"quantum":4,"peers":1,"enabled":true,"tempoRevision":0}
```

- `hostUs` is the SDK's monotonic host timestamp in integer microseconds. It uses QPC on Windows, `CLOCK_MONOTONIC_RAW` on Linux, and `mach_absolute_time` on macOS. Treat the origin as opaque. Electron main uses `performance.now() * 1000` in its own monotonic domain. Each renderer has its own `performance.now()` origin. Avoid wall-clock time and transferring a renderer's raw `performance.now()` value to another process without calibration. [SDK clocks](https://github.com/Ableton/link/tree/Link-4.1.1/include/ableton/platforms) · [Windows QPC](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)
- With main timestamps `sentUs` and `receivedUs`, the estimated helper-to-main offset is `(sentUs + receivedUs) / 2 - hostUs`. Add it to the helper timestamp to map the anchor into main. The timestamp is bracketed by the send and receipt, so the midpoint uncertainty is at most half the measurement's round trip at that instant, apart from clock resolution. The probe selects the lowest round trip among the last 20 samples. Asymmetric scheduling can bias the estimate and clock rates may drift. In Phase 2, calibrate each renderer against main with the same exchange or verify a common monotonic timebase, retain the lowest-delay measurements, and recalibrate after sleep or reload.
- `beat` is the helper's local Link beat position. At a matching `quantum`, `phase` is shared and expressed in beats in `[0, quantum)`. The prototype defaults to four beats and accepts `0.001` to `64` beats, rounded to the SDK's millionth-beat resolution. Compute elapsed beats as `(nowUs - mappedHostUs) / round(60_000_000 / bpm)`. Add to the beat and wrap the phase with positive modulo. Recompute for the current render timestamp. The SDK's display tempo is an approximation for extrapolation, and fresh anchors carry the SDK's clock corrections. [SDK phase and tempo semantics](https://github.com/Ableton/link/blob/Link-4.1.1/include/ableton/Link.hpp) · [Timing implementation](../desktop/src/main/linkTiming.js)
- BPM, beat and phase come from one SDK snapshot at the supplied host time. Replace the anchor when a newer snapshot arrives, including after tempo changes. `tempoRevision` counts SDK tempo callbacks separately and can briefly disagree with the captured BPM. At the prototype's 50 ms poll cadence, allow up to one poll interval plus Link propagation and process scheduling on an idle machine. Rendering can continue between polls. Pipe and Chromium scheduling can add jitter under GPU or CPU load. Sustained render-load and audio-to-photon latency are unmeasured.
- Phase naturally wraps at the quantum. Use a signed circular difference to compare predicted and received phase. A join, rejoin, or SDK clock correction can shift the grid, and a helper restart resets its local beat numbering and offset history. For Phase 2, mark stale samples and `peers=0` as unsynchronized. Use bounded free-run or fall back to local timing, clear calibration on helper restart, and re-anchor on the next valid sample. Where visual continuity matters, slew small corrections and apply large ones at a quantum boundary. Keep exact Link phase available internally for beat triggers, with a policy to prevent duplicate triggers across corrections. Test these policies before choosing thresholds.

## Packaging and licensing

The Windows release is NSIS x64 on Windows 10/11. The desktop build currently compiles and stages the Bun server and unpacks the prebuilt texture bridge. A future Windows job can check out the pinned Link SDK and submodule, build with CMake 3.16+ and Visual Studio 2022's C++ workload and Windows SDK, and stage the executable via Windows `extraResources`, for example under `resources/link`. Resolve it with `process.resourcesPath` in main, then verify DLL imports, licensing files, firewall discovery, signing, and process cleanup on the installed build. The prototype requests the static MSVC runtime (`/MT` for Release). Link uses Windows Winsock and IP Helper APIs. The timing-only `Ableton::Link` target uses standalone Asio. The Steinberg ASIO SDK and Link Audio are unnecessary for this build. Windows ARM64/x86 are outside the existing Spout package matrix. [Link build configuration](https://github.com/Ableton/link/blob/Link-4.1.1/cmake_include/ConfigureAbletonLink.cmake) · [Desktop workflow](../.github/workflows/desktop.yml) · [Current package layout](../desktop/electron-builder.yml)

HYDRACTRL's desktop code is `AGPL-3.0-only`. Ableton's SDK is GPL-2.0-or-later or separately licensed by Ableton. A candidate open-source route selects GPLv3 for Link and relies on AGPLv3 §13 for the combined native work, while keeping the HYDRACTRL source under its existing terms. The pinned standalone Asio dependency is Boost Software License 1.0. Before shipping, the maintainers should confirm the combined-work and installer treatment, the exact Corresponding Source and notices to offer for the SDK-bearing executable and bundle, and any obligations that apply when remote access is enabled. Confirm any Ableton branding or UI terms if using their branding or negotiating proprietary licensing. Phase 1 uses an external SDK checkout and adds no binary or dependency to the release. ## Validation

- Linux x64, GCC 14.2, CMake 3.31.10, official Link `4.1.1` with its pinned Asio submodule. The helper built and returned four-beat and 3.25-beat samples, rejected a nonfinite quantum, and exited on `quit` and EOF. After a forced kill of its pipe-owning parent, the helper exited with code 0 on EOF.
- Node 24 ran the same probe used by Electron main against the compiled helper and a separate C++ process using the real SDK on the same Linux host. The helper adopted an established peer's 123 BPM while that peer retained its tempo. In a separate run the peer count went `0 → 1 → 0 → 1`, and tempo changes by the other peer to 137, 91 and 143 BPM each incremented the revision. The 91 BPM command was reflected in the JS probe after 50.4 ms. Across 140 polled replies, round-trip latency was 0.144 ms median, 0.362 ms p95 and 1.661 ms maximum. Over 100 same-time comparisons at 137 BPM, wrapped phase differed by at most 0.000010 beats from the other SDK peer. Over 100 consecutive stable-tempo intervals, median native-clock extrapolation error was 0.00000021 beats and maximum was 0.00000095 beats. These phase checks use the same host clock for comparison and do not measure renderer or audio-to-photon latency.
- Repository checks passed with Bun 1.4.5. `bun test` passed all 535 tests with local networking enabled, `bun run lint` passed, `bun run build` built the client bundles, and electron-builder packaged a Linux x64 directory build. The default sandbox initially blocked an existing HTTP test, which passed when rerun with networking. Under Xvfb, `node scripts/smoke.mjs --dev --software-gl` with the built helper passed all 37 Electron 45 checks, including timing delivery to Electron main and clean helper exit on quit. The packaged Linux app passed its 35 checks.
- An LLVM-MinGW 23.1.6 cross-build on Linux produced a Windows x64 PE. The test sysroot needed case aliases for three Windows headers used by the SDK. The executable's imports were Windows system DLLs and Universal CRT API sets. The executable was neither run on Windows nor distributed. The intended MSVC x64 build and Windows installer path remain unverified.
- Ableton Live, its Tempo Follower, real Spout output, and end-to-end phase alignment remain untested. The Windows procedure below checks Live-to-helper timing and Spout coexistence. Renderer phase alignment needs the Phase 2 bridge.

## Windows test procedure

Use Windows x64 with Ableton Live, Bun, Node.js, Git, CMake, and Visual Studio 2022 Build Tools with **Desktop development with C++** and the Windows SDK. Use a normal network interface with multicast available. In PowerShell, start from a checkout of `feature/ableton-link`.

```powershell
git clone --branch Link-4.1.1 --recurse-submodules https://github.com/Ableton/link.git ..\ableton-link
git -C ..\ableton-link rev-parse HEAD
git -C ..\ableton-link submodule status
cmake -S desktop/link-prototype -B build/ableton-link -G "Visual Studio 17 2022" -A x64 "-DABLETON_LINK_DIR=$(Resolve-Path ..\ableton-link)"
cmake --build build/ableton-link --config Release
bun install --frozen-lockfile
Push-Location desktop
bun install --frozen-lockfile
# If Electron's executable is missing after install, run node node_modules/electron/install.js.
Pop-Location
$env:HYDRACTRL_LINK_PROBE = (Resolve-Path .\build\ableton-link\Release\hydractrl-link.exe).Path
@('sample', 'quit') | & $env:HYDRACTRL_LINK_PROBE
```

The expected SDK commit is `5ba907ae027a8c2ec8824463e37296dcefc5e9be` and the Asio revision is `8806a6803cde7054c3049d3666d3ec36786568c5`. With Live's Link disabled and no other peers, the terminal smoke check should return `enabled: true`, `peers: 0`, about 120 BPM, and a four-beat quantum. If Windows prompts for network access, allow Live and the helper on the trusted private network used for the test. [Ableton instructions for enabling Link](https://help.ableton.com/hc/en-us/articles/209072789-Enabling-Link-in-Live)

1. Quit any running HYDRACTRL desktop app. Leave Link disabled in Live and start the development app from `desktop` with `bun run start "--user-data-dir=$env:TEMP\hydractrl-link-phase1"`. The separate profile keeps the test away from your performance banks. Watch the console or use **Help → Show Logs**. Record the helper PID and confirm that it reports `peers=0` while beat and phase continue moving.
2. Enable Live's **Link** toggle under **Link** settings (or **Link/Tempo/MIDI** in older Live versions). Use a test set in 4/4 with global launch quantization of one bar, and leave **Follow** and Link **Start Stop Sync** off for the first check. On a network with just these two participants, Live and HYDRACTRL should each see one peer. Set Live to 123 BPM, then 96 BPM, and confirm each value and revision change in the HYDRACTRL log. Start and stop Live and confirm that Live transport responds to your own actions and the phase in HYDRACTRL keeps advancing.
3. Turn Link off in Live, wait for `peers=0`, and re-enable it. Check that the peer and BPM return without restarting HYDRACTRL. Then close HYDRACTRL normally. The log should record `helper exited` with code 0. Run `Get-Process -Id <PID> -ErrorAction SilentlyContinue` with the logged PID and verify that it returns no process. With Live still linked, set it to another BPM, relaunch HYDRACTRL, and verify that HYDRACTRL adopts Live's already-established BPM and leaves Live's tempo and transport as set. For a nondefault quantum, set `$env:HYDRACTRL_LINK_QUANTUM = '3'` before a launch and check that the reported phase wraps at three beats.
4. Clear any custom quantum with `Remove-Item Env:HYDRACTRL_LINK_QUANTUM -ErrorAction SilentlyContinue` and restart with the four-beat default. Enable Spout and observe the normal output in a receiver such as Resolume. Start and stop output while watching the Link log. Spout should behave as usual and the helper PID and samples should continue across output restarts. Record peer count, BPM, and round-trip times during normal workload. This checks coexistence. At Phase 1 the Spout frames do not consume Link timing.
5. For the party-audio check, on a Live version that supports Link and Tempo Follower together, select the sound-system input in Live's **Tempo & MIDI** settings, enable the **Follow** control, and use a clearly rhythmic input. Compare Live's BPM to the `[link]` log as the input tempo changes. Record Live and Windows versions, the network and output conditions, peer transitions, observed BPM and round trips, and the helper exit status. Phase-to-audio or phase-to-frame verification is a Phase 2 test. [Live 12 synchronization manual](https://www.ableton.com/en/manual/synchronizing-with-link-tempo-follower-and-midi/)
